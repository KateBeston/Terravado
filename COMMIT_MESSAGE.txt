Scaffold apps/main-site — the public login workspace (step 2 of the two-app split)

Context
Step 1 extracted the shared @terravado/engine + @terravado/domain packages.
This adds the second app: the MAIN SITE — the public-facing login workspace where
advisers, brokers, consultants and their clients work. It pulls the shared engine
+ domain packages and reads/writes the same (shared) Supabase. The internal portal
stays as-is for now; dividing which pages live where (and thinning the portal to
ops/admin) is the next step.

What's new
- apps/main-site — a second Next app in the monorepo, mirrored from the internal
  portal, importing @terravado/engine and @terravado/domain (transpilePackages).
  Its own package.json (terravado-main-site) and vercel.json (syd1, NO regwatch
  cron — that ingestion is internal-portal's job). No supabase/ migrations of its
  own: it shares the internal portal's database.
- Root scripts now cover both apps (dev:portal / dev:main, build:portal /
  build:main; typecheck + verify span the workspace).

Deploy
- Second Vercel project, Root Directory apps/main-site, same NEXT_PUBLIC_SUPABASE_*
  env as the portal (shared DB). The portal project stays on apps/internal-portal.

Known debt (next cleanup, flagged)
- The app-level backend (lib/data, lib/auth, lib/supabase, lib/domain/service+seed,
  lib/integrations, lib/modelling, lib/shortlist, lib/matching, lib/sharing,
  lib/regwatch, lib/deal, lib/format) and the components are currently DUPLICATED
  across both apps. The engine + domain (the crown-jewel logic and the DB schema)
  are already shared, so the two apps can't drift on the modelling or the data
  model — but the app-level backend can. Recommended follow-up: extract a shared
  packages/core (+ packages/ui) so both apps import one copy. Deferred so the
  main site stands up fast; worth doing before the two apps diverge much.
